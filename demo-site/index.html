Exhibit 02 · the race condition

    
Two Users, One Seat

    

      unit tests: all pass
      caught by: an integration test
    

    
A ticket-booking app. The code checks that the seat is free, spends 2–4 seconds
      processing payment, then writes the booking. Alice and Bob both tap seat
      B3 inside that window. The unit tests pass — they book seats one at a time,
      like polite robots. Real users are not polite robots.

        Click the same seat on both phones within ~2s — or let the button do it:

The fix is one atomic query: check and claim in a single step,
      so the database refuses the second buyer. Only a test that books concurrently —
      an integration test — ever sees this bug.

  


  
  

    
Exhibit 03 · the database has opinions

    
The Second Alice

    

      unit tests: all pass
      caught by: an integration test
    

    
A signup form. The table was created with username TEXT UNIQUE —
      a rule that lives in the database, not in the Python code. The unit tests check the
      validators and register "alice" exactly once. Then a second user also wants to be alice…


    

      

        
Buggy code
        
Two different users, same great idea. Click Sign up twice.

      

      

        
        
        
        

      

    


    

      

      

    


    
Constraints only fire against the real database — a unit test with
      fakes will never meet them. One integration test through the real API turns a
      500 crash into a polite "username taken".

  


  
  

    
Exhibit 04 · every test is green

    
The Discount That Never Left the Screen

    

      unit tests: all pass
      integration tests: all pass
      caught by: a manual test run
    

    
A checkout page. The backend's discount math is perfect — unit tested,
      integration tested, all green. But the frontend applies the discount to the screen…
      and forgets to put it in the payment request. The button promises ₹189.
      The card gets charged ₹210.


    

      

        
Buggy code
        
Apply the code, then hit Pay. Watch the receipt.

      

      

        

        

          

            
            
          

          

          
          

        

      

    


    

      

      

    


    
A green test suite only covers what somebody thought to test —
      no suite covers the code that isn't there. Before you ship:
      click through it like a real user.

  


  
  

    
Exhibit 05 · the change that broke the past

    
The Combo That Made Juice Free

    

      unit tests: all pass
      caught by: a regression pass
    

    
This pizza shop's pricing function ran correctly for months. Then the
      product team wanted a Lunch Combo, a developer refactored cart_total()
      to handle it, and the combo worked beautifully. So everyone tested the combo — and only the combo.
      Nobody re-tested a plain old cart. A lone juice now rings up at ₹0, and nobody will ever
      report it: customers don't complain about being undercharged.


    

      

        v1 — plain pricing, live for months
        NEW: 🍕 Pizza + 🧃 Juice = ₹199 Lunch Combo
        
        
      

      
On v1, price a juice. Then ship v2, test the combo
        (it works!) — and re-price that lone juice.

      

        

        

          

          
          

        

      

    


    

      
Release checklist — v2 “Lunch Combo”

      
What got tested before v2 went live. Click a box as you re-test that flow:

      
✓ NEW — pizza + juice rings up as a ₹199 combo

      
 single-item carts worked in v1 — never re-tested

      
 carts with no combo in them worked in v1 — never re-tested

      
 leftover pizzas / juices beyond the combo worked in v1 — never re-tested

    


    

      

      

    


    
The new feature worked. The suite was green. What broke was a flow that
      used to work — a regression — and the only thing that catches those is
      re-testing the past: a regression pass over every flow that already worked, every time
      shared code changes. Undercharges are the cruelest kind: overcharged customers write angry
      emails; undercharged ones stay very, very quiet.

  


  
  

    
Exhibit 06 · launch day, at launch scale

    
It Worked For One Fan

    

      functional tests: all pass
      caught by: a load test
    

    
A ticket drop: 120 tickets, released at a fixed time. Buying one takes about
      2 seconds — every functional test agrees it works. Then 200 fans show up in the same
      two seconds. The server's ~40 worker threads fill with payment delays, everyone else queues,
      and fan #200 waits 13 seconds to be told "sold out". Meanwhile the rest of the site
      is stuck in the same queue.

Nothing in this code is wrong — it has simply never been asked to do
      200 things at once. Functional tests ask "does it work?". A load test (Locust, k6,
      JMeter) asks "for how many, how fast, and where's the cliff?" — and it asks
      before launch day, because launch day will ask anyway.
